在 Apple Silicon Mac 上无痛试装 Omarchy:Try Omarchy 从黑屏抢救到远程访问全记录

发表于 2026-11-23 分类于 Linux

一、Omarchy 与 Try Omarchy 是什么

Omarchy 是 DHH(Ruby on Rails 作者)在 2025 年推出的 Arch Linux 发行版:Arch + Hyprland 平铺桌面 + 精心调好的 Quickshell 外壳,2026 年的 4.0 版本更是主打 AI 编程工作站——预置 Claude Code、Codex 等 agent,顶栏直接显示用量,口号是 “agentic Linux”。

它对 Mac 用户有个特殊优待:从 4.5(Omarchy M)开始,原生支持 Apple Silicon(M1/M2 首发完善,M3 可用)。体验方式有两种:

  1. 正式安装:双启动,动磁盘;
  2. Try Omarchy:一个原生 macOS App,以硬件加速虚拟机的方式把完整 Omarchy 桌面跑在窗口里,不分区、不动磁盘,还带摄像头/音频/剪贴板/共享文件夹透传。

本文走第二条路——「先试再买」。以下是 Apple Silicon(M1)+ macOS 26 + 国内网络环境下的完整踩坑实录,全部命令实测。

二、安装 Try Omarchy(顺利,5 分钟)

App 从 GitHub Releases 下载(v1.4.1,DMG 约 14 MB):

挂载 DMG,把 Try Omarchy.app 拖进「应用程序」即可。App 是 Developer ID 签名 + 公证的,Gatekeeper 直接放行。数据放在:

打开 App,点 Launch Omarchy,它会自动从 GitHub 下载约 3 GB 的系统镜像——第一坑来了。

三、坑一:内置下载器被网络卡死(13 MB / 3.2 GB)

App 内置下载器走的是 GitHub 的 release-assets CDN,国内直连会 SSL 重置;它似乎也不吃系统代理,进度条在 13 MB 处纹丝不动。等待无意义,直接读它的源码(开源在 omacom/try-omarchy)找手动注入的路。

3.1 源码里藏着三个关键事实

macos/Sources/OmarchyVMHelper/FactoryImageDownload.swift 写得很清楚:

  1. 清单内置在 App 里:Resources/guest/download.json 描述了完整镜像(约 3.23 GB,sha256 a8673906…)被切成 4 个字节段(3×1 GiB + 12 MB),每段有独立 URL 和 sha256;
  2. 落盘位置:shell-factory/<identity>.img.zst,<identity> 就是镜像内容摘要(8085b183…);
  3. 最重要的:下载器启动时先检查已存在的文件——如果 <identity>.img.zst 已存在且整体 sha256 匹配,直接跳过下载;即使只有半成品 .download 文件,也会逐段校验后续传。

也就是说:只要我手动把这 3.2 GB 拼好、校验好、放到它期望的位置,App 会自己接管。

3.2 aria2 多连接下载(单连接只有 200 KB/s,并行拉到 MB/s 级)

下载完成后按清单逐段校验,再拼接、整体校验、放到目标位置:

重新点 Launch Omarchy:App 校验已注入的镜像(约半分钟)→ 解压 → 启动,直接跳过下载。

经验:与其和下载器死磕,不如读懂它的校验逻辑,「帮它把活干完」。它自己会感谢你。

四、坑二:进桌面全黑——mesa 26.3.1 的 VirGL bug

镜像注入成功,VM 启动,首次设置(建账号)也走完了——然后桌面黑屏。

4.1 分层诊断法

黑屏是最难排查的故障,因为「哪一层挂了」有很多可能。我的路径:

  1. 看串口日志 shell/console.log:内核 7.3.0-75-omarchy 正常启动,到了 hzb login: 提示符 → Linux 本体活着;
  2. 看崩溃报告 ~/Library/Logs/DiagnosticReports/*.ips:App 在切换桌面空间时段错误于 qemu_console_listener_set_refresh——黑屏的后果而非原因;
  3. 客机内截屏(grim):QQ 那种「画面到底渲染了没」的问题,一张截图胜过十次猜:
  4. 搜官方仓库:Issue #470 症状完全吻合——Arch Linux ARM 的 mesa 升到 26.3.1 后,Qt Quick 的 GL 路径在 VirGL 上渲染全黑:Hyprland 和系统都活着,只有桌面外壳(Quickshell)画不出来。

复盘根因链:出厂镜像带的是好版本 mesa 26.2.7 → 进系统后跑了 omarchy update → 内核 7.3-72 升到 7.3-75 的同时 mesa 被拉到坏的 26.3.1 → 黑屏。更新本身就是坑的来源。

4.2 修复路线三选一

路线 可行性
① pacman 缓存降级 26.2.7 ❌ 缓存里只有新版本
② 升级到上游修复版 ❌ Omarchy 自建镜像源里只有 26.3.1-2,修复版未发布
③ 外壳强制软件渲染(官方 issue 验证过) ✅ 选它

关键证据来自 #470 评论区:LIBGL_ALWAYS_SOFTWARE=1 quickshell 能让壁纸和顶栏正常出现,且 Hyprland 本身不受影响。于是给外壳的启动器打补丁——找到 /usr/bin/omarchy-launch-shell 的 run_shell() 函数,在环境变量列表里插一行:

再用官方的 omarchy-restart-shell 重启外壳(它从 Hyprland 拉起新进程,保证环境干净)。验证方式很硬核:

4.3 坑三:截图有内容,屏幕还是黑的

补丁后客机内 grim 截图显示顶栏已经渲染(工作区、时钟、图标都在),但 Mac 窗口仍然全黑——这就是另一层的问题:VirGL 上下文丢失导致 scanout(扫描输出)死亡,App 自述文档里明写这是开放问题(“Lost GPU context leaves a permanent black desktop”)。

最优雅的解法:重置数据盘。删掉 shell/ 目录(64 GB 稀疏盘 + 状态),保留 shell-factory/ 里 20 GB 的解压出厂镜像,重新点 Launch——App 检测到没有数据盘,直接从出厂镜像克隆一个全新系统,几十秒完成,不用重新下载 3.2 GB。全新客机 = 好的 mesa 26.2.7 = 桌面正常显示。✅

经验:出厂镜像缓存就是你的「Time Machine」。动数据盘之前,先想清楚哪些是状态、哪些是资产。

五、固化:别让坑再来一次

进入新桌面后,第一件事不是体验,而是「打疫苗」:

5.1 锁死 mesa 版本

之后 omarchy update 照常更新其他包,mesa 永远停在 26.2.7。等官方 Issue #470 关闭后再解锁。

5.2 让客机网络走 Mac 的 Clash

Try Omarchy 的网络是 slirp NAT,客机的流量从 Mac 裸奔出去,不经过 Clash——国内站满速,国外站废掉。救星是 slirp 的特性:网关 10.0.2.2 就是宿主机的 loopback,也就是说客机可以直接用 Mac 上的 Clash:

内容都是 http_proxy=http://10.0.2.2:7890 一套 + no_proxy 豁免本地。重新登录会话后,Chrome 等 GUI 应用自动走代理。再给 Chrome 上双保险:

实测数据:国内直连 12.6 MB/s、走代理 1~2.4 MB/s(上限即 Clash 节点带宽)、DNS 0.07s。虚拟网络本身没有瓶颈,国外速度的天花板在节点。

六、远程访问:wayvnc + socat + Tailscale

需求:在学校用 Windows 控制家里的 Omarchy。方案分三层:

6.1 客机内:wayvnc(轻量 VNC 服务,Hyprland 原生兼容)

6.2 端口转发:改 settings.json(不用点 UI)

在 VM/v1/settings.json 的 portForwardingPreferences.mappings 里追加 {"guestPort": 5900, "hostPort": 5901, "protocol": "tcp"},重启 App 后 qemu 参数里就会出现 hostfwd=tcp:127.0.0.1:5901-:5900。

6.3 Mac 上:socat 中继 + LaunchAgent 常驻

App 的转发只绑定 127.0.0.1,局域网/远端设备够不着,用 socat 把它暴露出去:

同理再放一条 2223 → 2222 给 SSH 用。

6.5 Tailscale:跨网络的最后一块拼图

App Store 安装 Tailscale → 应用内登录 → 允许 VPN 配置(注意:只连上 VPN 不够,必须在应用里完成浏览器授权,否则 CLI 会报 Logged out)。Mac 拿到一个 100.x.x.x 的 tailnet IP。

Windows 端:安装 Tailscale(同一账号)+ TigerVNC Viewer,然后:

  • 远程桌面:VNC 地址填 100.x.x.x:5900(Mac 的 tailnet IP)
  • 远程终端:ssh -p 2223 hzb@100.x.x.x

从 Mac 本机对两个端口做握手自测,分别收到 RFB 003.008 和 SSH-2.0-OpenSSH_10.6——全链路打通 ✅。

七、最终状态与经验总结

项目 状态
桌面显示 ✅ 出厂 mesa 26.2.7,正常渲染
mesa 防护 ✅ IgnorePkg,坏版本进不来
客机网络 ✅ 国内 12.6 MB/s,国外自动走 Mac 的 Clash
远程桌面/终端 ✅ wayvnc :5900 + SSH :2223,经 Tailscale 跨网可达

几条可复用的经验:

  1. 下载器卡死 ≠ 只能干等:开源 App 的校验逻辑就是你的注入说明书——「帮它把活干完」比绕过它更稳;
  2. 黑屏要分层归因:串口日志看内核、.ips 看宿主崩溃、客机内 grim 看渲染、ufw status 看丢包——每层都有对应的证据,别猜;
  3. 先搜官方 issue 再造轮子:黑屏、下载卡死两个大坑都在官方仓库有记录,评论区的实测方案比自己发明靠谱;
  4. 重置数据盘是虚拟机的超能力:出厂镜像缓存 + 64 GB 稀疏盘的设计,让「重新安装」的成本从 3.2 GB 下载变成一次目录删除;
  5. 固化必须当场做:锁版本、写代理配置、注册常驻服务,都是在为下一次「看起来莫名其妙的故障」买保险。

现在这台 Mac 上躺着一个可远程访问的完整 Omarchy 桌面——Super+K 看快捷键,Super+Space 开启动器,AI agent 已就位。玩起来吧。
