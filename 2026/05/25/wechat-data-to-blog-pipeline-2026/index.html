从零打通微信数据到博客发布：一次 AI Agent 集成实践

发表于 2026-05-25 分类于 技术实践

前言

最近在做一个自动化工作流：把微信公众号上看到的好文章，自动提取、整理、发布到个人博客。

听起来很简单对吧？但实际上，它牵出了一整条技术链路——从 Windows 进程内存扫描，到 SQLCipher 数据库解密，再到 Hexo 博客构建部署。这篇文章就记录这个打通的过程和方法。

背景与目标

需求其实很直接：我有一个 Hexo 博客，希望每次在微信上看到有价值的公众号文章时，能自动或半自动地整理到博客上。

第一关：理解微信的数据存储

微信 4.x 的新格式

如果你很久没研究过微信桌面版的数据存储，可能会以为它还在用 WeChat Files 那个老目录。实际上，微信 4.x 版本引入了全新的存储体系——xwechat_files。

新的目录结构大致是这样的：

所有核心数据都存储在 SQLite 数据库中，但——这些数据库全部经过 SQLCipher 加密。

SQLCipher 是什么

SQLCipher 是 SQLite 的加密扩展，对每个数据库页面进行 AES 加密，并附带 HMAC 完整性校验。简单说，没有密钥，这些 .db 文件就是一堆乱码。

微信使用的是 SQLCipher 4，具体参数：

  • 加密算法：AES-256-CBC
  • 密钥派生：PBKDF2-HMAC-SHA512（256,000 次迭代）
  • 页面大小：4096 字节
  • 每个数据库有独立的 salt（存储在文件头的 16 字节中）

第二关：密钥在哪里

既然数据库是加密的，密钥在哪里？

答案在意料之中，也在情理之中：密钥存储在微信进程（Weixin.exe）的运行内存中。

进程内存扫描

Windows 上读取其他进程的内存，核心 API 是：

  1. OpenProcess — 打开目标进程，获取句柄
  2. VirtualQueryEx — 枚举进程的虚拟内存区域
  3. ReadProcessMemory — 读取指定内存区域的内容

但有个前提：需要管理员权限。因为 PROCESS_VM_READ 权限对非管理员进程是受限的。

从海量内存中找到密钥

微信进程的内存空间很大（动辄数 GB），直接全量扫描是不现实的。关键是要知道 找什么。

通过分析 SQLCipher 的密钥存储习惯，微信在内存中保存密钥的格式是：

这个模式非常具有辨识度：以 x' 开头，接着是 64 个 hex 字符（0-9, a-f），然后是可选的 32 个 hex 字符，最后以 ' 结尾。

扫描策略：

  1. 只扫描可写私有内存（PAGE_READWRITE + MEM_PRIVATE）——密钥存在堆上，不在代码段或映射文件中
  2. 使用 pymem.pattern_scan_all 搜索 x' 特征
  3. 对每个命中的位置，读取后续字节，验证 hex 格式
  4. 按出现频率排序，频率最高的就是正确的密钥

运行扫描后，从数十 GB 的虚拟地址空间中，可以提取到约 40-50 个候选密钥。

验证密钥的正确性

找到候选密钥后，需要验证它是否真的能解密数据库。验证方法很巧妙：

  1. 读取数据库文件的前 16 字节（salt）
  2. 用密钥和 salt 派生出 HMAC 密钥
  3. 校验数据库第一页的 HMAC 签名
  4. 匹配成功 → 密钥正确

意外发现：不同数据库用不同密钥

在验证过程中发现一个有趣的现象：同一个微信账号的不同数据库，使用的加密密钥不同。

数据库 密钥
biz_message_*.db（公众号消息） 密钥 A
session.db（会话） 密钥 B
contact.db（联系人） 密钥 C

这意味着不能用一个密钥解密所有数据库。这给那些只支持单密钥的工具带来了兼容性问题。

第三关：现有工具的局限

在探索过程中，尝试了两个主流的微信 CLI 工具：

wx-cli (@jackwener/wx-cli)

这是一个 Node.js 编写的 CLI 工具，提供了 18 个命令来查询微信数据。但它有两个关键问题：

  1. 只支持老版微信格式：它寻找的是 WeChat Files 目录路径，而微信 4.x 用的是 xwechat_files
  2. 单密钥模型：所有数据库共享一个 master_key，但微信 4.x 每个库的密钥不同

即使手动配置文件路径和密钥，也无法正常工作。

wechat-cli (@canghe_ai/wechat-cli)

另一个 Python 实现，自带内存密钥提取功能。但在 Windows 上安装受限：

  • npm 包只有 macOS arm64 二进制
  • pip 包需要 Python 3.10+（而很多 Windows 环境是 3.8/3.9）

解决方案：ZedeX/weixin-decrypte-script

最终使用的是这个开源工具集。它的优势在于：

  • Python 3.8+ 兼容，Windows 原生支持
  • 支持微信 4.x 的 xwechat_files 格式
  • 自动扫描进程内存提取密钥
  • 提供解密、读取、API 服务的完整工具链

经验与教训

1. 不要假设旧工具能用

微信的本地数据存储格式在 4.x 版本发生了根本性变化。很多基于旧版微信的工具已经失效。遇到问题时，第一反应应该是检查目标软件版本，而不是在错误的方向上调试。

2. 进程内存是宝藏

桌面应用的敏感数据（密钥、令牌、解密后的内容）几乎必然出现在进程内存中。只要有权访问进程内存，就能找到这些数据。这是很多所谓”本地加密”方案的软肋。

3. 不同工具之间互补

wx-cli 虽然不兼容新版本，但它的设计思路（AI 友好的 JSON 输出、命令式交互）值得借鉴。ZedeX 工具虽然解密能力强，但缺少一些高级查询功能。最终方案是组合使用：ZedeX 负责底层数据访问，上层自己构建业务逻辑。

4. 权限问题永远是门槛

读取进程内存需要管理员权限。这意味着这个工作流必须显式地以管理员身份运行。在自动化时要注意这一点。

隐私与安全说明

这套方法有几个天然的安全边界：

  • 完全本地运行：所有数据读取、解密、处理都在本地完成，不经过任何外部服务器
  • 只读操作：只读取进程内存和数据库文件，不修改任何微信数据
  • 可控输出：发布到博客的内容需要人工审核，不会自动公开私人信息

总结

打通微信数据到博客的技术路径不算短，但每一步都有清晰的逻辑：

  1. 数据在哪 → xwechat_files 目录下的 SQLCipher 加密数据库
  2. 密钥在哪 → 微信进程的运行内存中
  3. 怎么提取 → 通过 Windows API 扫描进程内存，匹配 x'<hex>' 特征
  4. 怎么解密 → 用提取的密钥 + 数据库头部的 salt 进行 SQLCipher 解密
  5. 怎么用 → 读取解压后的消息 → 提取文章 URL → 抓取全文 → 生成博客

这是一次典型的 AI Agent 工具集成实践：把多个开源工具、脚本和工作流串联起来，解决一个具体的自动化需求。本质上，就是让 AI Agent 拥有了”读取微信数据”的能力，然后基于这些数据完成更上层的任务。

如果你也在做类似的本地数据集成，希望这篇文章能给你一些参考。
